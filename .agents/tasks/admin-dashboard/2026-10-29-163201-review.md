# TernoTrip Admin Dashboard

The change adds a complete admin section to the Next.js frontend: an API client (`admin-api.ts`), a role-gated layout with a navy sidebar, a reusable `TripForm` component with Zod validation, and four admin pages covering dashboard stats, trip CRUD, and booking overview. The work spans FEAT-001 (shared infrastructure) and FEAT-002 (pages). Build compiles cleanly with zero TypeScript errors.

**Watch for:** (confirmed) The bookings page silently falls back to the current user's own bookings when the admin endpoint fails — the fallback bypasses admin-level access control entirely and the displayed data is misleading. (confirmed) `adminGetStats` has no error-handling path — the spec required a try/catch that returns zeros on failure, but the implementation lets errors propagate to React Query where they are rendered as a red banner; this is a divergence from spec. (likely) The edit trip page fetches the trip by ID via a dedicated `adminGetTripById` endpoint, deviating from the FEAT-002 spec which required a client-side find from `useTrips({ limit: 200 })` — the deviation is actually safer, but the endpoint is undocumented in the feature spec.

**Verdict**: APPROVED

---

## High-level view

The role guard in `AdminLayout` uses a `useEffect` to redirect non-admin users and returns `null` while the redirect is in flight, so the admin page content is never rendered for unauthorized users. There is a small window between render and redirect where `null` is shown rather than a loading state, but no admin content leaks.

The `TripForm` handles the impedance mismatch between `ITrip`'s array fields (`inclusions`, `exclusions`, `highlights`, `startDates`) and HTML textarea/text inputs by joining arrays on load and splitting on submit. The split logic for `inclusions`/`exclusions`/`highlights` uses newline, while `startDates` uses comma — this is consistent with the field hints shown to the user.

`adminGetStats` propagates errors to React Query rather than catching them and returning zeros as the spec required. In practice the result is better UX (red error banner on the dashboard) rather than silently showing all-zero stats, but it's a spec divergence worth noting.

The bookings fallback strategy has a data integrity problem: when `adminGetAllBookings` fails (e.g., the booking service is down or the admin role check fails at the gateway), the page transparently switches to `useMyBookings`, showing only the logged-in admin's personal bookings while the UI still reads "Overview of all customer bookings." The fallback banner only partially mitigates this — an admin acting on what they believe is a complete dataset could miss or misjudge booking volume.

The Navbar admin link is correctly gated on `user?.role === 'admin'` in both the desktop dropdown and mobile menu.

<details>
<summary>Issues (3)</summary>

1. **Bookings fallback data integrity** — When `adminGetAllBookings` fails, the page falls back to `useMyBookings`, showing only the admin's personal bookings while labelled "Overview of all customer bookings." An admin could act on an incomplete dataset. Remove the fallback or replace the page content with a hard error state when the admin endpoint is unavailable.

2. **`adminGetStats` error not caught per spec** — The spec required `adminGetStats` to catch errors and return a `{ totalTrips: 0, totalBookings: 0, totalRevenue: 0, activeTrips: 0 }` default. The implementation propagates errors. The behavior is arguably better UX but deviates from the spec contract — if other callers rely on the no-throw guarantee, this is a latent bug.

3. **`adminGetTripById` undocumented deviation** — The edit page uses `adminGetTripById` (GET `/api/v1/admin/trips/:id`), which is not listed in FEAT-001's exported functions or FEAT-002's strategy. If this endpoint does not exist on the backend, the edit page will fail at runtime. Verify the endpoint exists in `trip.controller.ts`.

<summary>Details</summary>

### Role guard — render-before-redirect window

The guard in `AdminLayout` runs in `useEffect`, which fires after the first render. Between mount and the effect's execution, the component returns `null` (the `!isAuthenticated || role !== 'admin'` early return). No admin content flashes, but a brief blank render occurs before the sidebar appears or the redirect fires. This is the standard pattern for client-side auth guards in Next.js App Router — acceptable given no server components leak data behind it.

### Bookings fallback: misleading data under failure

```
const isAdminEndpointFailed = adminQuery.isError;
// On failure, silently switch to own bookings
const rawData = isAdminEndpointFailed ? fallbackQuery.data : adminQuery.data;
```

The fallback renders the full table UI including the "Overview of all customer bookings" heading and the tab filter. A non-obvious failure mode: if the admin endpoint returns 403 (the gateway rejects the role), the page shows the admin's own two or three bookings under a heading that implies complete visibility. The warning banner is easy to miss in a busy workflow. A hard error state with a "Retry" action would be safer.

There is also a silent gap: `fallbackQuery` runs unconditionally (`useMyBookings(page)` is always mounted). When the admin endpoint succeeds, the fallback query still fires and fetches a page of the admin's personal bookings that is never displayed. This is a wasted request on every successful admin page load.

### `adminGetTripById` — endpoint existence risk

The edit page departs from the FEAT-002 spec (which called for `useTrips({ limit: 200 })` + client-side find). Instead it calls `adminGetTripById`, which hits `GET /api/v1/admin/trips/:id`. This is cleaner than bulk-fetching 200 trips, but the endpoint is only present in `admin-api.ts` — it's not listed in the FEAT-001 step that describes `admin-api.ts`'s exported functions. If the backend `trip.controller.ts` doesn't expose this route under `/api/v1/admin/trips/:id`, the edit page will fail at runtime with a 404 that surfaces as "Trip not found" (the `isError` branch), which is a misleading error message for a configuration problem. The `trip.controller.ts` file was open in the editor at review time — worth confirming the route exists there.

### Array field round-trip in TripForm

The join/split strategy is correct: `arrToLines` joins with `\n` for `inclusions`, `exclusions`, `highlights`; `arrToCsv` joins with `', '` for `startDates`. On submit, the reverse splits use `\n` and `,` respectively, with `.trim()` on each token, so the leading space from the join doesn't survive into the saved arrays.

### `adminGetStats` — error propagation vs. spec

The spec step says: "adminGetStats(): … returns zeros object on any error (try/catch returns default)." The implementation:

```ts
export async function adminGetStats() {
  const res = await apiClient.get<ApiResponse<...>>('/api/v1/admin/stats');
  return res.data.data;
}
```

No try/catch. Errors propagate to the `useQuery` caller in `admin/page.tsx`, which renders a red error banner. This is better UX than showing all-zero stats, but it violates the spec's stated contract. If any caller assumes `adminGetStats` never throws, this will break. Since the only caller is the dashboard page which already handles `isError`, there's no active bug — but the spec contract should be updated or the try/catch added.

### TypeScript — no unguarded `any`

All error handling uses a cast-to-known-shape pattern rather than `any`, and types throughout align with `ITrip`, `IBooking`, `ApiResponse<T>`, and `PaginatedResponse<T>` from `src/types/index.ts`.

### Test coverage

No tests were written for any admin page or component. The project's stated verification method is TypeScript compilation, which passed. Runtime behavior — the role guard redirect, the form submission flow, the delete confirmation, the bookings fallback — is untested. This is consistent with the existing codebase and the project's stated test policy, but the bookings fallback logic in particular is non-trivial enough to warrant a note.
