# Admin dashboard: role-gated sidebar, trip CRUD, bookings overview

The change adds a complete admin section: a role-gated layout with a navy sidebar, an API client layer (`admin-api.ts`) for trip and booking mutations, a reusable `TripForm` with Zod validation, and four admin pages (dashboard home, trips table, new/edit trip, bookings). Access control lives in the layout's `useEffect` — non-admin users are redirected to login with a `returnUrl`. The Navbar conditionally surfaces an "Admin Dashboard" link only when `user.role === 'admin'`.

Watch for: (1) **confirmed** — `adminGetStats` silently swallows all errors and returns zeros, masking auth failures and 5xx responses on the dashboard; (2) **confirmed** — the edit page fetches up to 200 trips client-side to find one by `_id`, which breaks silently for any trip beyond position 200 in the list; (3) **confirmed** — delete errors in `admin/page.tsx` and `trips/page.tsx` are swallowed in `finally` with no user feedback; (4) **confirmed** — the api-client's `protectedPaths` list doesn't include `/admin`, so a session expiry during an admin mutation won't trigger the redirect-to-login path.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The role guard in `AdminLayout` is structurally sound — it checks both `isAuthenticated` and `user?.role === 'admin'` before rendering, and the `useEffect` fires on every auth state change. The gap is that it relies solely on client-side auth state; a sufficiently determined user who can craft a valid session token as a non-admin would only be stopped at the API layer, which is the correct place to enforce it anyway.

`admin-api.ts` correctly delegates all auth to the gateway's cookie-based session and adds no manual role headers. The `adminGetStats` silent-zero fallback is intentional per the spec but is too broad — it hides network errors and server errors from the admin, making the stats row unreliable as a health indicator.

The edit-trip page uses `useTrips({ limit: 200 })` to load all trips and find one by `_id`. This is a deliberate workaround for a slug-only public API, acknowledged in FEAT-002. It becomes a silent failure mode once trip count exceeds 200, and it loads every trip's full data on every edit page visit.

`TripForm`'s array field handling — newline-split for inclusions/exclusions/highlights, comma-split for startDates — is consistent between `arrToLines`/`arrToCsv` on the way in and the split logic on the way out. The one risk is startDates: the form accepts free-text ISO strings with no date validation, so a malformed date passes Zod and reaches the API.

Error handling is inconsistent across the admin pages. The new/edit trip pages surface server errors correctly via `extractErrorMessage` and the `serverError` prop. The delete handlers in both `admin/page.tsx` and `trips/page.tsx` use `try/finally` with no `catch`, so a failed delete silently closes the confirm modal — the admin sees nothing wrong.

The `api-client.ts` token-refresh path redirects to login only when the current page is in a hard-coded `protectedPaths` list (`/checkout`, `/bookings`, `/notifications`, `/profile`). `/admin` is not in that list, so a 401 from a mutation mid-session will reject silently without redirecting the admin user to login.

<details>
<summary>Issues (5)</summary>

1. **Silent delete failures** — `handleDelete` in both `admin/page.tsx` and `trips/page.tsx` uses `try/finally` with no `catch`. A failed API call closes the modal and shows nothing. Add a `catch` block that sets a visible error state.

2. **adminGetStats swallows all errors** — the `try/catch` in `admin-api.ts` returns zeros for any failure (network down, 401, 5xx). The dashboard stats row will silently show zeros with no indication of a problem. Either let the error propagate and handle it in the page, or at minimum distinguish auth/network errors from expected-empty responses.

3. **Edit page trips-list cap at 200** — `useTrips({ limit: 200 })` silently fails to find any trip added after the first 200. This should either use a dedicated `GET /api/v1/admin/trips/:id` endpoint, or at minimum display an error when `!trip && !isLoading` rather than an "empty" state that looks like a missing route.

4. **api-client protectedPaths missing `/admin`** — on a 401 after token refresh failure, the client only redirects to login when the current path is in `['/checkout', '/bookings', '/notifications', '/profile']`. `/admin` is absent, so session expiry during any admin mutation silently rejects and the admin stays on the page with no feedback. Add `/admin` to `protectedPaths` in `api-client.ts`.

5. **startDates accepts malformed ISO strings** — the Zod schema treats `startDates` as a plain `z.string()` with no date format validation. A typo like `"2025-13-45"` passes client validation and reaches the backend. Add a `.refine()` that validates each comma-split token as a parseable date before submission.

<summary>Details</summary>

### Silent delete failures in admin/page.tsx and trips/page.tsx

Both delete handlers are structured identically:

```ts
try {
  await adminDeleteTrip(deleteId);
  queryClient.invalidateQueries({ queryKey: ['trips'] });
} finally {
  setIsDeleting(false);
  setDeleteId(null);
}
```

When `adminDeleteTrip` throws, the `finally` block still clears `deleteId`, closing the confirm modal. The UI returns to normal with no error message. The admin has no way to know the delete failed. The fix is a `catch` block that sets a `deleteError` string rendered inside the modal.

### adminGetStats error masking

```ts
} catch {
  return { totalTrips: 0, totalBookings: 0, totalRevenue: 0, activeTrips: 0 };
}
```

This catch has no binding — it swallows every error class including network failures, 401s from a revoked session, and 500s from a broken stats endpoint. The dashboard will show `0 / 0 / 0 / ₹0` with no visual distinction from a legitimate empty state. The page should either receive the error via `useQuery`'s `isError` state (by removing the try/catch from the API function) or the catch should at minimum rethrow on non-404 status codes.

### Edit page 200-trip cap

`useTrips({ limit: 200 })` returns at most 200 trips. Any trip created after the list exceeds that size will yield `trip === undefined`, which renders an `EmptyState` ("Trip not found") with a "Back to Trips" button. There's no indication that the trip exists but wasn't loaded — it looks identical to a deleted or invalid trip. Given that a dedicated admin fetch-by-id endpoint isn't available yet, the page should at least show a different message when `data` loaded successfully but the trip wasn't in the result set.

### api-client session expiry gap

The token-refresh interceptor in `api-client.ts` redirects to login only for paths in `protectedPaths`:

```ts
const protectedPaths = ['/checkout', '/bookings', '/notifications', '/profile'];
```

`/admin` is not listed. If a refresh fails while an admin is creating or editing a trip, the mutation rejects silently, the form stays open, and the admin has no indication their session ended. Adding `'/admin'` to this array ensures the standard redirect behavior.

### startDates date validation gap

The TripForm schema:
```ts
startDates: z.string(),
```

On submit, the string is split by comma and passed directly to the API as `startDates: string[]`. No token is validated as an actual date. The backend may or may not validate this further, but the form gives false confidence via Zod validation passing with malformed inputs. A `.refine()` on the schema field or a per-token parse check in `handleFormSubmit` would catch this before the network call.
